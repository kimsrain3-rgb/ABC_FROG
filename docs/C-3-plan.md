## 0. 무엇을 하려는가

지금은 아이가 퍼즐을 **다 맞춘 뒤에야** 보상 영상을 받기 시작한다.
느린 회선이면 **제일 신나는 순간에 화면이 멈춰 있다.**

퍼즐을 맞추는 **10~30초 동안 뒤에서 미리 받아두어**, 완성하는 순간 바로 나오게 한다.

**C-2 와의 관계** — C-2 는 "영상을 가볍게" 만들었다(2g 기준 76→14MB). C-3 는 그 가벼워진 영상을 **미리** 받는다. 둘은 곱하기로 작동한다: 400KB 를 30초 동안 미리 받는 것과 2,400KB 를 완성 직후에 받는 것은 체감이 전혀 다르다.

★ **반드시 `__vq.pick()` 을 거친 주소를 미리 받아야 한다.** 원본을 받아놓고 400 을 또 받으면 두 배가 된다.

## 1. 조사 결과 (2026-08-18 실측)

### 1.1 ★ "다음에 나올 영상"은 언제 정해지는가 — **전부 처음부터 안다**

**C-3 의 성립 여부를 가르는 질문이었다. 결론: 성립한다.**

| 퍼즐 | 순서를 정하는 것 | 언제 정해지나 |
|---|---|---|
| 공룡 | `ANIMALS[]` 고정 배열 + `animalIdx` 가 0부터 1씩 증가 (`dino.html:70,122,251`) | **문서 열릴 때 이미 10개 전부** |
| 동물 | 같은 구조 (`animal.html:68,82,228`) | **문서 열릴 때 이미 10개 전부** |
| 파닉스 | `WORDS[]` 고정 배열 + `CUR` 이 0부터 1씩 증가 (`phonics/index.html:126,444`) | **문서 열릴 때 이미 6단어 18편 전부** |
| 과일 | `WP_ORDER[]` 고정 배열 (`script.js:1464`) | **처음부터.** 단 영상은 10번째 끝나고 **딱 1편** |

**섞기(shuffle)는 순서에 관여하지 않는다.** 파닉스의 `shuffle()`(`:255`)은 **글자 타일 배치**만 섞고, 공룡·동물의 `Math.random()`은 **조각 놓인 위치·기울기**만 흔든다. 어느 것도 "다음 영상"을 바꾸지 않는다.

→ **완성 직전에 정해지는 것이 아니라, 퍼즐이 열리는 순간 이미 전부 확정돼 있다.** 미리 받을 수 있다.

#### 파닉스는 구조가 하나 더 유리하다

파닉스는 **한 단어에 영상이 3편 연속**으로 붙는다(`sit_dog` → `sit_cat` → `sit_raccoon`, 사이 간격 `GAP=1600ms`). 즉 **1편이 재생되는 5~7초 동안 2편을 미리 받을 수 있다.** 공룡·동물에는 없는 여분의 창이다.

### 1.2 지금 퍼즐 한 판에서 무엇을 언제 받는가 — **거의 안 받는다**

라이브 `dino.html` 실측(PerformanceResourceTiming):

| 순서 | 파일 | 크기 | 시작 | 끝 |
|---|---|---|---|---|
| 1 | `error-tracker.js` | 5KB | 0.27초 | 0.47초 |
| 2 | `video-quality.js` | 5KB | 0.48초 | 0.70초 |
| 3 | `dino_trex_image.jpg` (퍼즐 조각 + 밑그림 겸용) | **270KB** | 0.78초 | 1.04초 |
| 4 | `bgm.mp3` (문서당 1회) | **758KB** | 0.83초 | 1.48초 |
| — | **그 뒤 아이가 퍼즐을 맞추는 내내** | — | **아무것도 안 받는다** | |

**★ 이것이 C-3 의 근거다.** 퍼즐이 뜨고 1.5초면 받을 게 끝나고, 그 뒤 **10~30초 동안 네트워크가 통째로 비어 있다.** 미리받기를 얹을 여유가 있는 정도가 아니라 **완전히 놀고 있다.**

한 판 자원 크기(평균):

|---|---|---|---|---|---|
| 공룡 | 468KB | 59KB | 2,187KB | 645KB | **401KB** |
| 동물 | 635KB | 51KB | 2,403KB | 639KB | **398KB** |
| 파닉스 | (글자 타일, 그림 없음) | 8KB | 1,770KB | 627KB | **384KB** |
| 과일 | — | — | 700KB (엔딩 1편) | — | — |

### 1.3 ★ 퍼즐 하나 맞추는 데 몇 초 걸리는가 — **지금은 알 수 없다**

**GA4 에 `elapsed_ms` 는 있지만 우리가 원하는 값이 아니다.**

`elapsed_ms` 는 **`error-tracker.js` 안에만** 있고(`:39,163`), 뜻은 **"앱이 켜진 뒤 몇 ms 만에 에러가 났는가"** 다. 퍼즐 시간과 무관하다.

퍼즐 관련 이벤트는 있다 — `word_puzzle_open` / `word_puzzle_complete`(`script.js:1504,1551,1591,1563,1602,2462`). 그런데 **둘 다 시각 정보를 안 싣는다.** GA4 표준 보고서는 "같은 사람의 open 과 complete 를 짝지어 간격을 구하는" 계산을 못 한다(BigQuery 내보내기가 있어야 한다).

→ **퍼즐 소요 시간은 지금 데이터로는 못 구한다. 새로 재야 한다.** (아래 3.1 — 0단계)

### 1.4 이미 받아둔 것을 어떻게 알아보는가 — **주소가 글자 하나까지 같아야 한다**

브라우저는 **주소 문자열이 완전히 같을 때만** 캐시를 재사용한다. 그래서 두 가지를 확인했다.

**① 캐시 꼬리표가 매번 바뀌지 않는가 — 안 바뀐다. 다행이다.**

| 퍼즐 | 꼬리표 | 값 |
|---|---|---|
| 공룡 | `bust()` → `ASSET_VER` | `'20260817'` **고정 문자열** (`dino.html:130`) |
| 동물 | 같음 | 고정 |
| 파닉스 | `VID_VER` | `'?v=20260811'` **고정** |
| 과일 | 하드코딩 | `'?v=20260817'` **고정** |

★ `index.html` 의 **코드 로더**(`?b=Date.now()`)와 헷갈리면 안 된다. 그건 `script.js`/`style.css` 전용이고, **영상·그림에는 안 붙는다.** 영상 꼬리표는 전부 날짜 고정이라 **미리받기 주소와 재생 주소를 똑같이 만들 수 있다.**

**② 서버가 캐시를 얼마나 허락하는가 — 10분.**

```
GitHub Pages 응답:  Cache-Control: max-age=600     (10분)
                    ETag: "..."  /  Accept-Ranges: bytes
```

미리받기와 재생 사이 간격은 **10~30초**다. 10분 안이라 **재검증 없이 그대로 캐시에서 나온다.** 문제 없다.

### 1.5 방법별 실측 — 어느 방식이 실제로 통하는가

라이브에서 같은 파일(400 티어, 404KB)로 조건을 맞춰 측정. **"준비까지"** = `<video>` 가 `canplaythrough` 될 때까지.

| 방식 | 준비까지 | 재생 순간 네트워크 | 비고 |
|---|---|---|---|
| **C. 미리받기 없음 (지금)** | **265ms** | **404,371 byte 새로 받음** | 기준선 |
| A. `fetch()` 로 미리 받기 | **47ms** | **0** | ✅ |
| B. `<link rel=preload as=video>` | **55ms** | **0** | ⚠️ 콘솔 경고 |
| D. 숨은 `<video preload=auto>` | **44ms** | 300 byte (헤더만) | ✅ |

세 방식 다 **재생 순간의 다운로드를 0 으로 만든다.** 이 PC 는 회선이 빠르므로 265ms 라는 차이가 작아 보이지만, **2g 에서는 이 404KB 가 30~60초**다. 그 30~60초가 0 이 된다.

**B 는 탈락.** 크롬이 `<link rel=preload> uses an unsupported 'as' value` 경고를 낸다 — `as="video"` 는 크로미움이 지원하는 값이 아니다. 어쩌다 통한 것이고, 우리 `error-tracker.js` 가 지켜보는 콘솔에 경고를 남긴다.

**D 는 가능하지만 무겁다.** 미리받기용 `<video>` 요소를 하나 더 만들면 **디코더 자원을 잡는다.** 저사양 기기를 신경 쓰는 이 프로젝트에서 굳이 택할 이유가 없다.

**→ A(`fetch`) 를 택한다.** 이유: ⓐ 켜고 끄고 중단(`AbortController`)이 전부 우리 손 안에 있다 ⓑ 미디어 디코더를 안 만든다 ⓒ 실패하면 그냥 아무 일도 안 일어난다 ⓓ 이미 집에 같은 패턴이 있다(`script.js` 의 `_frogPump()` — 대기줄 + 동시 2개 제한).

### 1.6 🔴 가장 위험한 것 — **받는 중에 재생이 시작되면 두 배로 받는다**

일부러 재현해 측정했다. `fetch` 를 시작하고 **30ms 뒤**(아직 받는 중) 같은 주소로 `<video>` 재생을 시작:

```
fetch  전송 2,031,843 byte
video  전송 2,031,843 byte      ← 같은 파일을 처음부터 다시
──────────────────────────
합계   4,063,686 byte           (파일은 2,475,000 byte)
```

**브라우저는 진행 중인 같은 요청을 합쳐주지 않는다.** 아이가 미리받기가 끝나기 전에 퍼즐을 완성하면 — **느린 회선일수록 그럴 확률이 높다** — 오히려 **두 배를 받는다.** C-3 가 도우려던 바로 그 사람을 가장 크게 해치는 구조다.

**이 하나가 C-3 설계의 중심이다.** 아래 3.4 에서 다룬다.

⚠️ 위 측정은 전부 **PC 크롬**이다. 앱은 **안드로이드 WebView** 라, 캐시 재사용은 **실제 폰에서 다시 확인해야 한다**(2.5 검증 항목).

## 2. 설계

### 2.1 공용 파일 1개 — `video-prefetch.js` (신규)

C-2 와 같은 구조. 호출 지점이 서로 다른 문서(iframe)라 변수 공유가 안 되므로 공용 파일로 간다.

```
video-quality.js    ← C-2. 어느 화질을 줄지 고른다        (기존)
video-prefetch.js   ← C-3. 그 주소를 미리 받아둔다        (신규)

dino.html / animal.html : video-prefetch.js
phonics/index.html      : ../video-prefetch.js     ← 한 칸 위
```

**왜 `video-quality.js` 안에 넣지 않는가**: 파일 하나에 일 하나. 섞어 두면 **C-3 를 되돌릴 때 C-2 파일을 건드려야 한다.** 라이브 서비스에서 되돌리기가 어려워지는 쪽은 택하지 않는다. (대신 요청이 1건 늘지만 5KB 짜리다.)

**의존 관계**: `video-prefetch.js` 는 반드시 `video-quality.js` **뒤에** 읽는다. `__vq` 가 없으면 **아무 일도 하지 않는다**(미리받기 안 함 = 지금 동작).

### 2.2 내놓는 것

| 이름 | 하는 일 |
|---|---|
| `__vp.warm(url)` | 그 주소를 **미리 받아둔다.** 내부에서 `__vq.pick()` 을 거친다 |
| `__vp.ready(url)` | 재생 직전에 부른다. **받는 중이면 끝날 때까지 기다린 뒤** 진행한다 (1.6 해결) |
| `__vp.cancel()` | 화면을 벗어날 때 받던 것을 중단한다 |
| `PREFETCH_ON` | `false` 한 글자로 **전체 무력화** (C-2 의 `FORCE_ORIGINAL` 과 같은 자리) |

★ 주소는 **`pick()` 먼저, 캐시 꼬리표 나중** — C-2 에서 확인된 순서 그대로다. 미리받기 주소와 재생 주소를 **같은 함수로 만들어** 두 곳이 어긋날 수 없게 한다.

★ 허용목록도 `__vq.pick()` 을 그대로 쓴다. 즉 **보상 영상이 아닌 주소(개구리 webm·그림·소리)는 미리받기 대상이 될 수 없다.**

### 2.3 ★ 몇 개를 미리 받을 것인가 — **다음 1개만**

**"많을수록 좋다"가 아니다. 1개가 정확히 맞는 수다.**

| | 근거 |
|---|---|
| **2개째의 이득이 0 이다** | 1개를 미리 받아두면, 그 영상이 재생되는 동안 + 다음 퍼즐을 맞추는 동안 = **또 한 번의 온전한 창**이 생긴다. 2개째는 그때 받아도 늦지 않다. **미리 받아서 벌 수 있는 시간이 없다** |
| **안 볼 영상을 받는다** | 아이가 3번째 공룡에서 그만두면, 4번째는 봤지만 5번째는 낭비다. 1개만 받으면 **낭비는 최대 1편(400KB)** 으로 고정된다 |
| **느린 회선일수록 1개도 벅차다** | 2g 에서 400KB 는 30~60초다. 퍼즐 한 판이 그 정도다. **2개를 걸면 첫 개도 제때 못 끝난다** — 1.6 의 두 배 받기가 터진다 |
| **되돌리기가 쉽다** | 동시에 도는 요청이 하나면 중단·재개가 단순하다 |

**파닉스만 예외적으로 "1개 앞"의 뜻이 다르다.** 한 단어에 3편이 붙어 있으므로:

```
글자 맞추는 중   → 1편 미리받기
1편 재생 중      → 2편 미리받기      ← 5~7초의 여분 창
2편 재생 중      → 3편 미리받기
3편 끝 → 다음 단어 글자 맞추는 중 → 다음 단어 1편 미리받기
```

**항상 "지금 필요한 것 하나 앞"** 이라는 규칙은 같다. 동시에 도는 요청은 언제나 **1개**다.

### 2.4 ★ 언제 시작할 것인가 — **조각 개수가 아니라 "내 그림이 다 온 뒤"**

**조각을 몇 개 맞춘 뒤로 정하지 않는다.** 이유:

- 조각은 **그림이 다 와야 생긴다.** 그림이 오기 전엔 맞출 조각 자체가 없으므로 "3조각 뒤"는 사실상 "그림 온 뒤"의 부정확한 대체품이다
- 조각 수는 퍼즐마다 다르다(공룡·동물 6조각, 과일 4~9조각, 파닉스는 글자 수). **한 기준으로 못 쓴다**
- 우리가 진짜 피하려는 것은 **"퍼즐 그림과 영상이 회선을 두고 다투는 것"** 이다. 그걸 직접 막는 조건이 정확하다

**시작 조건**

```
퍼즐 그림 load 완료  →  1.5초 더 기다림  →  미리받기 시작
```

1.5초를 더 두는 이유: 첫 판은 `bgm.mp3`(758KB)가 그림과 같이 오고 있고, 아이가 **화면을 처음 만지는 순간**이라 여기가 가장 버벅이면 안 되는 구간이다. 1.5초는 1.2절 실측(그림·bgm 이 1.5초에 끝남)에서 나온 값이다.

파닉스는 퍼즐 그림이 없으므로 **화면이 만들어진 뒤 1.5초**로 같게 둔다.

### 2.5 ★ 느린 회선에서 오히려 해가 되지 않는가 — **검토 결과: 끄지 않는다. 단 조건이 있다**

**"2g 에서는 아예 끄는 게 낫지 않은가"를 진지하게 따져봤다. 답은 '아니다'이지만, 이유가 중요하다.**

| 걱정 | 실제 | 결론 |
|---|---|---|
| 퍼즐 조각 그림 받는 중에 영상까지 받으면 버벅인다 | **그림이 다 온 뒤에만 시작**한다(2.4). 그리고 1.2절 실측대로 **그 뒤로는 받는 게 하나도 없다** — 다툴 상대가 없다 | 해당 없음 |
| 게임이 느려진다 | 퍼즐 맞추기는 **받아놓은 그림을 캔버스에 그리는 일**이라 네트워크와 무관하다. 다운로드는 다른 스레드다 | 해당 없음 |
| 다음 퍼즐 그림과 다툰다 | 아이가 다음 판으로 넘어가면 **`cancel()` 로 중단**한다 | 설계로 해결 |
| 🔴 **받는 중에 완성해 두 배로 받는다** | **2g 에서 가장 잘 터진다.** 400KB 가 30~60초인데 퍼즐도 그 정도다 | **`ready()` 로 반드시 막는다 (3.4)** |

**끄지 않는 진짜 이유**: 2g 는 **C-3 가 존재하는 이유**다. 4g 유저는 미리받기가 없어도 0.3초면 받는다. 30~60초를 기다리는 사람이 바로 2g 유저다. **도와야 할 사람에게서 기능을 빼는 것은 앞뒤가 안 맞는다.**

**단, `ready()` 가 없으면 켜지 않는다.** 두 배로 받는 위험이 이득보다 크다. → **0단계에서 `ready()` 를 먼저 넣는다.** (C-2 에서 "폴백 없이는 티어 파일을 붙이지 않는다"와 같은 원칙)

### 2.6 `saveData=true` 인 사람 — **미리받기 끔**

| | |
|---|---|
| **결정** | `navigator.connection.saveData === true` → **미리받기 안 함** |
| **왜** | 데이터 절약을 **본인이 직접 켠 사람**이다. 미리받기는 본질적으로 **"안 볼 수도 있는 것을 미리 받는" 투기**다. 절약하겠다는 사람의 데이터로 투기하지 않는다 |
| **손해는?** | 이 사람은 C-2 로 이미 **400 티어(400KB)** 를 받는다. 완성 후 받아도 원본 대비 1/6 이다. **덜 나쁜 상태는 이미 확보돼 있다** |
| **확인 방법** | GA4 에 `reason=savedata` 로 몇 명인지 이미 잡히고 있다(C-2, 2026-08-17) |

### 2.7 되돌리기 3단계 (C-2 와 같은 구조)

| 단계 | 방법 | 효과 |
|---|---|---|
| 1 | `video-prefetch.js` 의 **`PREFETCH_ON = false`** | 한 글자. **모든 화면에서 미리받기 즉시 중단**, 나머지는 그대로 |
| 2 | 해당 단계 커밋 `git revert` | 그 퍼즐만 되돌림 |
| 3 | 백업 태그 `backup-before-prefetch-20260818` | 착수 전 상태로 |

★ `PREFETCH_ON=false` 여도 **`__vq`(C-2)는 그대로 돈다.** C-3 를 꺼도 영상은 여전히 회선에 맞게 가볍다.
★ C-2 의 `FORCE_ORIGINAL` 처럼, 켜 둔 걸 잊지 않도록 **GA4 에 `killswitch` 로 남긴다**(3.5).

### 3.4 🔴 `ready()` — C-3 의 핵심

```
재생 직전:
  받아둔 게 있다        → 그대로 진행 (캐시에서 즉시)
  아직 받는 중이다      → ★ 그 요청이 끝날 때까지 기다린 뒤 진행   ← 두 배 받기 차단
  미리받기를 안 했다    → 그대로 진행 (지금 동작과 동일)
  미리받기가 실패했다   → 그대로 진행 (C-2 의 원본 폴백이 받아준다)
```

**"기다리는 게 손해 아닌가"** — 아니다. 미리받기는 **더 일찍 시작했으므로** 기다려도 남은 양이 항상 더 적다. 반대로 안 기다리면 **처음부터 다시 받는다**(1.6 실측: 2.4MB 파일에 4.06MB 전송).

**대안 — `objectURL`**: `fetch` 로 받은 blob 을 `URL.createObjectURL()` 로 재생하면 **캐시에 의존하지 않고 100% 확실**하다. 다만 **파일을 통째로 RAM 에 들고 있어야 한다**(400KB~2.4MB). 이 프로젝트는 저사양 기기 RAM 에 민감하므로(CLAUDE.md 그림 픽셀 상한 규칙) **1안은 캐시 방식**으로 가고, **실제 폰 검증에서 WebView 가 캐시를 재사용하지 않으면 그때 objectURL 로 바꾼다.**

## 4. 검증 방법

### 4.0 🔴 먼저 — **브라우저는 영상을 몇 바이트 받았는지 안 알려준다**

검증 방법을 짜다가 발견했고, **원래 계획을 통째로 바꿔야 했다.**

처음엔 `PerformanceResourceTiming` 의 `transferSize` 로 "재생 순간에 몇 바이트가 흘렀는가"를 재려 했다. 그런데 **`<video>` 의 다운로드는 여기에 기록될 때도 있고 안 될 때도 있다.**

같은 라이브 주소로 **미리받기 없이** 영상 3편을 연속 재생한 실측:

| 회차 | 실제로 받았나 | `ready_ms` | resource timing 기록 |
|---|---|---|---|
| 1 | 받음(400KB) | 255ms | **0건** |
| 2 | 받음 | 70ms | **0건** |
| 3 | 받음 | 299ms | **0건** |

분명히 받았는데 **기록이 하나도 없다.** (앞선 다른 측정에서는 잡히기도 했다 — 즉 **믿을 수 없다.**)

**→ 바이트를 세는 방식은 검증 수단으로 쓸 수 없다.** 대신 **아이가 실제로 기다린 시간(`ready_ms`)** 을 잰다. 어차피 우리가 신경 쓰는 것도 바이트가 아니라 **기다림**이다.

**기준선은 이미 확보했다** (같은 파일·같은 회선, PC 크롬):

| | `ready_ms` |
|---|---|
| 미리받기 **성공** 후 재생 | **44 / 47 / 55ms** |
| 미리받기 **없이** 재생 | **255 / 265 / 299ms** |

**5배 이상 갈린다.** 느린 회선일수록 이 차이는 훨씬 커진다. 즉 `ready_ms` 하나로 "재사용됐는가"를 판정할 수 있다.

★ 예외적으로 **바이트를 직접 셀 수 있는 곳이 딱 하나 있다 — 실제 폰의 앱별 데이터 사용량**(4.1-C). 그래서 실제 폰 확인이 더 중요해졌다.

---

### 4.1 ★ "미리 받은 것이 실제로 재사용되는가" — 이 작업의 최대 실패 시나리오

받아놓고 또 받으면 **데이터가 두 배**다. 네 가지 방법으로 겹쳐 확인한다.

#### A. `ready_ms` 비교 (개발 중 기본 확인)

같은 파일·같은 회선에서 **미리받기 O / X** 를 번갈아 재서 표로 만든다.
**판정**: 미리받기 O 가 X 의 **1/3 이하**면 재사용된 것. 비슷하면 재사용 실패다.

#### B. 회선을 조여서 다시 (차이를 크게 만들어 확실히)

DevTools 로 **Slow 3G** 를 걸고 A 를 반복한다. 빠른 회선에서는 255 vs 47ms 라 눈에 안 띌 수 있지만, 조이면 **수십 초 vs 0.1초**로 갈려 착각할 여지가 없다.

#### C. 🔴 실제 폰 앱별 데이터 사용량 (결정적 — **바이트를 직접 센다**)

**브라우저가 안 알려주는 바이트를 안드로이드가 알려준다.** 사장님이 직접 하실 수 있다.

```
① 폰 설정 → 네트워크/연결 → 데이터 사용량 → 앱별 → ABC Frog 의 현재 숫자를 적는다
② 앱을 완전 종료했다 켜고, 공룡 퍼즐 딱 한 판만 하고 영상까지 다 본다
③ 다시 같은 화면에서 숫자를 적는다. 차이를 낸다
```

| 결과 | 뜻 |
|---|---|
| 약 **1.5MB** (그림 270 + 소리 59 + bgm 758 + 영상 400) | ✅ **정상. 한 번만 받았다** |
| 약 **1.9MB 이상** (영상 400KB 가 두 번) | 🔴 **두 배 받기 발생** |

★ Wi-Fi 를 끄고 **모바일 데이터로** 해야 앱별 사용량에 잡힌다.
★ 2번째 판부터는 bgm 이 캐시라 숫자가 줄어드는 게 정상이다.

#### D. 라이브 상시 감시 (사람이 안 봐도 잡히게)

GA4 에 `result` 와 `ready_ms` 를 남긴다(5장).
**`result=hit`(미리받기 성공) 인데 `ready_ms` 가 크면 = 미리 받아놨는데 재생 때 또 받고 있다는 뜻**이다. 이게 쌓이면 **사람이 검사하지 않아도 실패가 드러난다.**

> CLAUDE.md 규칙 — *"자동으로 도는 것을 만들 때는 '실패해도 알 수 있는가'를 반드시 함께 설계한다."* D 가 그 장치다.

### 4.2 ★ `pick()` 주소와 미리받기 주소가 정확히 일치하는가

**원본을 미리 받아놓고 400 을 또 받는 사고**를 막는 부분이다. 세 겹으로 막는다.

#### ① 코드로 애초에 어긋날 수 없게 (가장 중요)

**주소를 만드는 함수를 한 개만 둔다.** 미리받기와 재생이 **각자 주소를 조립하지 않는다.**

```
❌ 위험한 구조                        ✅ 갈 구조
warm(pick(A.video) + 꼬리표)          function urlOf(A){ return bust(__vq.pick(A.video)); }
vid.src = bust(pick(A.video))         warm(urlOf(A))   /   vid.src = urlOf(A)
   ↑ 두 곳이 각자 조립 = 언젠가 어긋난다        ↑ 한 곳만 고치면 둘 다 따라온다
```

C-2 에서 **`pick()` 먼저·꼬리표 나중** 순서를 두 번이나 강조해야 했던 이유가 이것이다. 순서를 지키라고 주석으로 부탁하는 대신 **틀릴 수 없게 만든다.**

#### ② 자동 감시 — 어긋나면 조용히 두 배 받지 말고 **신고하게**

`ready(url)` 이 받은 주소와 `warm()` 이 받아둔 주소를 **문자열로 비교**한다. 다르면 GA4 에 `result=mismatch` 를 보낸다.
→ 사고가 나도 **라이브에서 즉시 드러난다.**

#### ③ 검증 시 전수 대조

**회선 8종 × 퍼즐 3종**에서 미리받기 주소와 재생 주소를 나란히 찍어 비교한다.

| 조건 | 미리받기 | 재생 | 같아야 함 |
|---|---|---|---|
| `4g` | `videos/…mp4?v=…` | 동일 | ✅ |
| `3g` | `videos_650/…` | 동일 | ✅ |
| `2g`·`slow-2g` | `videos_400/…` | 동일 | ✅ |
| `?vq=400` 강제 | `videos_400/…` | 동일 | ✅ |
| `saveData` | **(미리받기 없음)** | `videos_400/…` | — |

★ 특히 **`?vq=` 강제에서 미리받기가 원본으로 새지 않는지**를 본다. 강제 스위치는 부모 창 주소까지 보므로(C-2), iframe 안에서 잘못 읽으면 여기서 어긋난다.

---

### 4.3 캐시 꼬리표(`?v=`)가 바뀌면 미리 받아둔 것이 무효화되는가

#### 결론: **자동으로 무효화된다. 그리고 한 세션 안에서는 바뀔 수 없다.**

| | |
|---|---|
| **무효화되는가** | 주소 문자열이 다르면 브라우저에겐 **완전히 다른 파일**이다. 옛 주소로 받아둔 것은 그냥 안 쓰이고 새로 받는다 |
| **바뀔 수 있는가** | `ASSET_VER`·`VID_VER` 는 **문서가 열릴 때 정해지는 상수**다(1.4). 미리받기와 재생은 **같은 문서 안**에서 일어나므로 그 사이에 값이 바뀔 수 없다. 배포로 값이 바뀌면 iframe 이 새로 열리며 새 값으로 통일된다 |

**확인 방법**: 미리받기 후 `?v=` 만 바꿔 재생 → `ready_ms` 가 **미리받기 없을 때 수준으로 오르는지**(=새로 받았는지) 본다.

#### ⚠️ 다만 C-3 가 증상을 하나 늘린다

**영상을 같은 파일명으로 교체하고 `ASSET_VER`/`VID_VER` 를 안 올리면** — 원래도 옛 영상이 나오는 문제였는데, 이제 **옛 영상을 미리 받아두기까지 한다.** 문제가 커지진 않지만 **낭비가 한 겹 는다.**

→ 배포 체크리스트에 그대로 둔다: **영상 갈아끼운 날엔 꼬리표 날짜를 반드시 바꾼다**(`phonics/` 와 `test/phonics/` 두 곳).

### 4.4 🔴 실제 폰(안드로이드 WebView) — PC 크롬으로 대체 불가

1.5·1.6·4.0 측정은 **전부 PC 크롬**이다. 앱은 **안드로이드 WebView** 라 미디어 캐시 동작이 다를 수 있다. **여기서 재사용이 안 되면 C-3 는 이득이 0 이면서 데이터만 두 배 쓰는 기능이 된다.**

#### 확인 항목

| | 방법 |
|---|---|
| **미리받은 것이 재생 때 재사용되는가** | 4.1-C (앱별 데이터 사용량) — **가장 결정적** |
| 저사양 기기에서 퍼즐 맞추는 동안 버벅임이 없는가 | 실제 조작 |
| 비행기모드에서 미리받기 실패 시 게임이 안 멈추는가 | 실제 조작 |
| 미리받기 도중 앱을 백그라운드로 → 복귀 | 실제 조작 (vc11 의 `onResume` 조건부 reload 와 겹치는 구간) |

#### ★ 재사용이 안 되면 — objectURL 로 전환한다 (전환 계획을 미리 확정해 둔다)

**전환 판정 기준 (숫자로 미리 못 박는다)**

> GA4 에서 **`result=hit` 인데 `ready_ms` 중앙값이 1,500ms 를 넘는 상태가 3일 이상** 지속되면 전환.
> (미리받기가 성공했는데도 오래 걸린다 = 캐시를 안 쓰고 있다는 뜻)

**전환 방법**

```
지금(1안 · 캐시 방식)
   fetch(url) → 본문 버림 → v.src = url          ← 브라우저 캐시에서 나오길 기대

바꿈(2안 · blob 방식)
   fetch(url) → blob 을 들고 있음
   v.src = URL.createObjectURL(blob)              ← 캐시에 의존하지 않음. 100% 확실
   재생 끝 / 화면 이탈 → URL.revokeObjectURL() + blob 참조 해제
```

**대가 = RAM.** 파일 하나를 통째로 메모리에 든다. 이 프로젝트는 저사양 기기 RAM 에 민감하므로(CLAUDE.md 그림 픽셀 상한 규칙 — 2026-07-28 에 그것 때문에 기기가 죽었다) **상한을 규칙으로 못 박는다.**

| 규칙 | 이유 |
|---|---|
| **항상 1편만 보관.** 새로 `warm()` 하면 이전 blob 즉시 `revoke` | 쌓이면 그때가 사고다 |
| **`4g`(원본 2.4MB)에서는 blob 방식을 쓰지 않는다.** 650·400 티어에서만 | 4g 는 미리받기 이득이 0.3초인데 RAM 부담은 6배다. **손해 보는 거래** |
| 화면 이탈·뒤로가기 시 즉시 `revoke` | 누수 차단 |

**🔴 전환 시 반드시 같이 고쳐야 하는 것 — C-2 폴백이 깨진다**

C-2 의 원본 폴백은 이렇게 생겼다:

```js
var orig = __vq.original(v.currentSrc || v.src);   // 티어 주소 → 원본 주소
```

blob 방식이면 `v.src` 가 **`blob:https://…` 형태**라, `original()` 이 `/videos_400/` 을 찾지 못해 **폴백이 통째로 죽는다.**
→ blob 방식으로 갈 때는 **원래 http 주소를 따로 기억해 두고 폴백에 그것을 쓴다.** (전환 작업의 필수 항목이며, 빠뜨리면 C-2 의 안전장치를 잃는다.)

### 4.5 기능 · 회선 · 안전

#### 기능

- 미리받기 시작 시점이 **그림 load + 1.5초** 인지
- 마지막 공룡/동물/단어에서 **미리받기를 안 하는지** (다음이 없다)
- 파닉스 3편 연쇄가 **1편 앞**을 지키는지 (동시 요청 항상 1개)
- 미리받기 도중 강제로 완성시켰을 때 **`ready()` 가 기다렸다 진행하는지** (`result=wait`)

#### 회선

| 조건 | 기대 |
|---|---|
| `4g` | 원본 미리받기 |
| `3g` / `2g` / `slow-2g` | **650 / 400 티어** 미리받기 (원본 아님) |
| `saveData=true` | **미리받기 안 함**, 재생은 400 으로 정상 |
| `?vq=` 강제 | 강제한 티어를 미리받기 |
| 미리받기 중 뒤로가기 | **중단**되고 요청이 남지 않음 |
| `PREFETCH_ON=false` | 미리받기 0건, 게임 정상, GA4 `result=off` |

#### 안전

- `__vq` 가 없을 때 / `fetch` 실패 / gtag 없음 → **게임 정상, JS 에러 0건**
- 개구리 webm·그림·소리가 **미리받기 대상이 되지 않는지** (`__vq.pick()` 허용목록 재사용)
- **C-2 원본 폴백이 그대로 동작하는지** — 티어 파일을 일부러 없애고 확인
- 회귀: `script.js`·`style.css`·`index.html`·`video-quality.js`·`error-tracker.js` 미변경
- 라이브 curl 200 + 용량 확인

## 5. 효과 측정 — GA4

### 5.1 무엇을 판단해야 하는가

C-3 는 **"아이가 덜 기다리게 됐는가"** 하나를 위한 작업이다. 그런데 그건 **재는 순간이 두 번**이어야 알 수 있다.

> 메모리 규칙 — *"고치기 전/후를 같이 재기. 기준선 없는 검증은 무의미."*

**그래서 0단계에서 계측만 먼저 켠다.** 미리받기는 아직 아무 데도 안 켠 상태로 `video_prefetch` 를 **`result=off` 로** 보내면, 며칠 만에 **"미리받기가 없을 때 아이가 실제로 몇 초 기다렸는가"** 라는 **기준선**이 쌓인다. 1단계부터는 같은 지표가 얼마나 내려가는지 **바로 비교**된다.

### 5.2 남길 것

#### 이벤트 ① `video_prefetch` — 보상 영상 1편당 1회, **재생을 시작하는 순간**

| 파라미터 | 값 | 뜻 |
|---|---|---|
| `result` | `hit` / `wait` / `miss` / `off` / `savedata` / `fail` / `mismatch` | 미리받기가 어떻게 됐나 |
| `ready_ms` | 숫자(밀리초) | **주소를 넣고 → 재생 준비될 때까지.** ★ 아이가 실제로 기다린 시간 |
| `wait_ms` | 숫자(밀리초) | `ready()` 가 미리받기 끝나길 기다린 시간 (`hit` 이면 0) |
| `lead_ms` | 숫자(밀리초) | 미리받기 시작 → 재생 요청까지. **미리받기에 주어졌던 창의 크기** |
| `puzzle` | `dino`/`animal`/`phonics` | ★ **이미 등록된 것 재사용** |
| `tier` | `4g`/`650`/`400` | ★ **이미 등록된 것 재사용** |

**`result` 값의 뜻**

| 값 | 뜻 |
|---|---|
| `hit` | 미리받기가 **제때 끝났다** — 목표 상태 |
| `wait` | 아직 받는 중이라 **기다렸다** (그래도 두 배 받기는 막았다) |
| `miss` | 미리받기를 **안 했다** (마지막 편이라 다음이 없었음 등) |
| `off` | **비상 스위치가 꺼 놓은 상태** — 0단계의 기준선이 이 값으로 쌓인다 |
| `savedata` | 데이터 절약 모드라 **일부러 안 했다**(확정 ①) |
| `fail` | 미리받기가 **실패**했다 (네트워크 끊김 등) |
| `mismatch` | 🔴 **미리받은 주소와 재생 주소가 달랐다** (4.2-② 자동 감시) |

#### 이벤트 ② `word_puzzle_complete` — **기존 이벤트에 `solve_ms` 1개만 추가**

| 파라미터 | 값 | 비고 |
|---|---|---|
| `solve_ms` | 숫자(밀리초) | 퍼즐 열림 → 완성. **확정 ③** |

⚠️ 공룡·동물은 완성 신호가 **iframe → 부모 `postMessage`** 로 간다(`{t:'dino_done', key:…}`). `solve_ms` 도 **그 메시지에 실어 보내야** 한다.

**🔄 2026-08-18 갱신 — 파닉스는 이미 끝났다**
파닉스 완성 이벤트를 C-3 와 별개로 먼저 넣으면서(커밋 `0716fd4`) **`solve_ms` 도 파닉스만 함께 붙였다.** 같은 파일을 두 번 건드리지 않으려고 한 번에 정리한 것이다.
→ **0단계에서 `solve_ms` 를 붙일 대상은 공룡·동물·과일 3곳이다.** 파닉스는 건드리지 않는다.
→ 6장 발견 ⑤("파닉스에 완성 이벤트가 없다")도 **해소됐다.**

**🔄 `puzzle` 추가 계획은 취소했다**
원래는 `word_puzzle_complete` 에 `puzzle` 을 더해 이미 등록된 측정기준을 재사용하려 했다. 대신 **`category` 를 등록하는 쪽으로 바꿨다** — 라이브 코드를 하나도 안 건드리고, **기존 공룡·동물·과일 이벤트가 그 즉시 쪼개 보인다.** 라이브 서비스에서는 코드를 덜 건드리는 쪽이 낫다.

### 5.3 🔴 사장님이 등록하실 것 — **새로 7개** (이름 확정)

오늘 등록하신 5개(`tier`·`reason`·`effective_type`·`save_data`·`puzzle`)는 **그대로 쓴다.** `tier` 는 C-3 에서도 같은 뜻이라 **다시 등록할 필요 없다.**

**🔄 2026-08-18 갱신 — 5개 → 7개.** 파닉스 완성 이벤트(커밋 `0716fd4`)를 넣으면서 `category`·`word` 두 개가 더 필요해졌다. **둘 다 이미 라이브에서 보내고 있던 값**인데 등록이 안 돼 있어서 보고서에서 안 보이던 것들이다 — 등록하는 순간 **공룡·동물·과일·파닉스 넷 모두** 쪼개 보인다.

#### ⚠️ 탭이 두 개다 — 숫자는 '측정기준'이 아니라 '측정항목'에 등록해야 한다

**관리 → 데이터 표시 → 맞춤 정의** 안에 탭이 두 개 있다.

- **맞춤 측정기준(Dimension)** = 글자·분류 (`hit`, `dino` 같은 것)
- **맞춤 측정항목(Metric)** = 숫자 (평균·합계를 낼 수 있는 것)

🔴 **`ready_ms` 같은 숫자를 측정기준에 등록하면 못 쓴다.** 밀리초 값 하나하나가 각각 다른 줄로 잡혀서 표가 수천 줄이 되고 평균이 안 나온다.

#### 등록 목록

**① 맞춤 측정기준 (Dimension) — 3개**

| 측정기준 이름 | 범위 | 이벤트 매개변수 | 언제부터 데이터가 있나 |
|---|---|---|---|
| 퍼즐 종류 | 이벤트 | `category` | **이미 쌓이는 중** (과일·동물·공룡·파닉스) |
| 낱말 | 이벤트 | `word` | **이미 쌓이는 중** — ★ 이게 **이탈 지점**을 보여준다 |
| 미리받기 결과 | 이벤트 | `result` | C-3 1단계부터 |

★ `category`·`word` 는 **지금 당장 등록하는 게 이득이 가장 크다.** 라이브가 이미 보내고 있어서, 등록하는 순간부터 파닉스 완주율이 바로 쌓인다.

**② 맞춤 측정항목 (Metric) — 4개 · 측정 단위 전부 `밀리초`**

| 측정항목 이름 | 범위 | 이벤트 매개변수 | 측정 단위 |
|---|---|---|---|
| 재생 준비 시간 | 이벤트 | `ready_ms` | **밀리초** |
| 미리받기 대기 시간 | 이벤트 | `wait_ms` | **밀리초** |
| 미리받기 확보 시간 | 이벤트 | `lead_ms` | **밀리초** |
| 퍼즐 완성 시간 | 이벤트 | `solve_ms` | **밀리초** |

⚠️ **등록한 시점 이후 데이터만** 쪼개 보인다(소급 안 됨) — C-2 때와 같다. **0단계 배포 전에 등록해 두는 것이 가장 좋다.**
※ GA4 한도는 측정기준 50개 / 측정항목 50개다. 여유는 충분하다.

### 5.4 며칠 뒤 무엇을 보고 판단하는가

**보는 곳**: 탐색 → 자유 형식 → 행에 `미리받기 결과`, 값에 `이벤트 수` + `재생 준비 시간(평균)` → 이벤트 이름을 `video_prefetch` 로 필터

| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| `hit` 비율 높고 `ready_ms` 작다 | ✅ **C-3 작동 중. 목적 달성** | 그대로 |
| 🔴 `hit` 인데 `ready_ms` 가 크다(>1,500ms) | **미리 받아놨는데 재생 때 또 받고 있다** = WebView 캐시 재사용 실패 | **objectURL 전환**(4.4) |
| `wait` 비율이 높다 / `wait_ms` 가 크다 | 미리받기가 퍼즐 시간 안에 못 끝난다 | 시작을 앞당기거나, 2g 티어를 더 줄이는 것 검토 |
| `lead_ms` 가 `ready_ms` 대비 넉넉하다 | 창이 남는다 | 2편 미리받기를 그때 재검토 |
| 🔴 `mismatch` 가 보인다 | **주소가 어긋났다.** 원본과 티어를 둘 다 받고 있을 수 있다 | 즉시 조사 |
| 🔴 `off` 가 보인다(1단계 이후에도) | **비상 스위치를 켜 놓고 잊었다** | 끄기 |
| `fail` 이 보인다 | 미리받기 자체가 실패 | 원인 조사 |
| `solve_ms` 중앙값 | **퍼즐 한 판에 몇 초 걸리는가** — 1.3 의 미해결 질문 답 | 미리받기 창 설계의 근거 |

**전/후 비교**: 0단계(`result=off`) 기간의 `ready_ms` **중앙값** vs 1단계 이후 `hit` 의 `ready_ms` 중앙값. 이 두 숫자의 차이가 **C-3 가 아이에게 돌려준 시간**이다.

## 6. 조사 중 발견한 것

> C-2 때 조사 중 발견한 *'영상 실패 시 조용히 넘어감'* 이 작업 순서를 바꿨다. 이번에도 계획을 바꾼 것들이 있다.

| | 발견 | 계획에 미친 영향 |
|---|---|---|
| ① 🔴 | **받는 중에 재생이 시작되면 두 배로 받는다.** 실측 2.4MB 파일에 4.06MB 전송 (1.6) | **`ready()` 가 C-3 의 중심이 됐다.** 0단계에 넣고, 없으면 1단계를 시작하지 않는다 |
| ② 🔴 | **브라우저가 영상 다운로드 바이트를 안 알려준다.** `PerformanceResourceTiming` 이 `<video>` 를 기록할 때도 있고 안 할 때도 있다 (4.0) | **검증 방법을 통째로 바꿨다.** 바이트 대신 `ready_ms`(기다린 시간)로 잰다. **실제 폰 데이터 사용량**(4.1-C)이 바이트를 세는 유일한 수단이 됐다 |
| ③ | **`elapsed_ms` 는 퍼즐 시간이 아니다.** `error-tracker.js` 안에만 있고 "앱 켜진 뒤 에러까지 걸린 시간"이다 (1.3) | 퍼즐 시간을 **새로 재야 한다** → 0단계에 `solve_ms` 추가(확정 ③) |
| ④ | **`<link rel=preload as="video">` 는 크로미움이 지원하지 않는다.** 콘솔 경고를 낸다 (1.5) | 미리받기 방식에서 **탈락**. `fetch` 로 확정 |
| ⑤ | **파닉스에는 완성 이벤트가 없다.** `phonics_open` 만 있고 `word_puzzle_complete` 도 `postMessage` 도 없다 | GA4 에서 **파닉스는 "열었다"만 알고 "다 했다"를 모른다** → ✅ **2026-08-18 해소**(커밋 `0716fd4`). C-3 와 별개로 먼저 넣었고 `solve_ms` 도 파닉스만 함께 붙였다 |
| ⑥ | **objectURL 로 바꾸면 C-2 원본 폴백이 죽는다.** `v.src` 가 `blob:` 이라 `__vq.original()` 이 티어 폴더를 못 찾는다 | 전환 계획에 **"원래 http 주소를 따로 기억"** 을 필수 항목으로 못 박았다 (4.4) |
| ⑦ | **캐시 꼬리표가 전부 고정 문자열**이다(`ASSET_VER='20260817'`, `VID_VER='?v=20260811'`). `Date.now()` 가 아니다 | ✅ **미리받기 주소와 재생 주소를 같게 만들 수 있다.** C-3 성립의 전제 하나가 해결됐다 |
| ⑧ | **GitHub Pages 는 `Cache-Control: max-age=600`(10분)** 을 보낸다 | 미리받기~재생 간격은 10~30초라 **10분 안. 문제 없다** |
| ⑨ | 퍼즐 그림이 **조각용·밑그림용 두 군데서 쓰이는데** 주소가 같아 실제로는 **1번만 받는다** | 확인만. 문제 없음 |

## 7. 위험 정리

| 위험 | 대비 |
|---|---|
| 🔴 **받는 중 완성 → 두 배 받기** | `ready()` 로 차단. **0단계에서 먼저 넣고, 없으면 1단계를 시작하지 않는다** (1.6 / 4.1) |
| 🔴 **WebView 가 캐시를 재사용 안 함** | 실제 폰 데이터 사용량으로 확인(4.1-C) + GA4 상시 감시(5.4). 안 되면 **objectURL 전환**(4.4) |
| 🔴 **실패해도 모르고 지나감** | 브라우저가 바이트를 안 알려준다(4.0). → `ready_ms`·`mismatch` 를 GA4 에 남겨 **앱이 스스로 신고**하게 한다 |
| 🟡 티어 주소와 미리받기 주소 불일치 | 주소를 **한 함수**로만 만든다 + `mismatch` 자동 신고 (4.2) |
| 🟡 objectURL 전환 시 C-2 폴백 사망 | 전환 항목에 **"원래 http 주소 따로 보관"** 을 필수로 명시 (4.4) |
| 🟡 화면 벗어난 뒤에도 계속 받음 | `cancel()`. 검증 4.5 |
| 🟡 파닉스 `../` 경로 실수 | 파닉스를 3단계로. 앞 둘로 방식 검증 후 착수 (C-2 와 동일) |
| 🟢 안 볼 영상을 받는 낭비 | 1개 앞으로 제한 → 최대 400~650KB |
| 🟢 영상 교체하고 꼬리표 안 올림 | 낭비가 한 겹 늘 뿐, 새 위험은 아님. 배포 체크리스트 유지 (4.3) |
| 🟢 미리받기 자체가 고장 | 전 구간 try-catch. 실패 = **지금 동작** |
