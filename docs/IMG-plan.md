**Slow 3G에서 과일 퍼즐 첫 그림까지 40.5초**(사장님 실측). 3~7세 아이가 빈 화면을 40초 본다.

### 1.6 ★ WebP — 사장님 결과와 제 결과가 갈렸다. 원인을 찾았다

사장님: *"수박은 PNG가 작았고 파인애플은 WebP가 더 컸다"*
제 계산: 10장 중 **9장에서 WebP가 이겼다**

**정반대인 이유 = 무손실이냐 손실이냐다.**

| 수박 1,670KB | 크기 |
|---|---|
| PNG 256색 | **181KB** |
| **WebP 무손실** | **968KB** ← 사장님이 만드신 게 이쪽으로 보인다 |
| **WebP 손실(q80)** | **73KB** |

**사장님 결과가 틀린 게 아니다.** 무손실 WebP는 PNG보다 5배 크다. **손실 WebP는 그 1/13이다.**
→ **손실 WebP를 후보에 반드시 포함해야 한다.** 다만 손실이므로 **대조 시트에서 눈으로 확인하고 결정한다**(5장).

### 1.7 안드로이드 WebView에서 WebP가 되는가 — **된다. 확인 완료**

- 앱 `minSdk 24` = **안드로이드 7.0 이상**만 설치된다(`twa-project/app/build.gradle:11`)
- WebView는 안드로이드 5부터 **크로미움 기반**이고, **손실 WebP + 알파는 안드로이드 4.2.1부터** 지원된다
- 즉 **우리 앱의 가장 낮은 기기도 WebP 지원 범위 안에 한참 들어와 있다**

⚠️ 그래도 **실제 폰 최종 확인은 한다**(5장). "지원한다"와 "우리 화면에서 잘 나온다"는 다른 문제다.

### 1.8 그림을 두 번 받고 있지는 않은가 — **확인했다. 정상이다**

C-2 때 동물·공룡에서 *"퍼즐 조각 그림을 두 번 받던 회귀"*(커밋 `b7f4c64`)가 있었으므로 과일도 확인했다.

**콜드 캐시로 `peach` 측정**:
```
img 개시  전송 1,889,710 byte   ← 실제 다운로드
css 개시  전송         0 byte   ← 캐시에서 (같은 주소)
합계      1,889,710 byte = 파일 크기 1배
```
→ **정상. 중복 다운로드 없다.**

※ 처음 측정에서는 997KB가 두 번 찍혀 보였으나, **캐시가 낀 측정 오독**이었다. 콜드 캐시로 다시 재서 확인했다.

## 5. 검증 방법

### A. 🔴 대조 시트 (필수)

**기계 검사는 뭉개짐을 못 잡는다.** C-2에서 쓴 방식을 그대로 쓰되, **퍼즐 특유의 조건을 더한다.**

**시트 ① — 전체 그림 3단**: `원본 / PNG256 / WebP q80`을 나란히. 10장.
**시트 ② — 🔴 조각 확대 보기**: 실제 조각 크기(1.2 실측값)로 잘라내 **폰 화면에서 보이는 그대로** 3단 비교.
  → 전체를 축소해 보면 차이가 안 보이는데 조각으로 보면 보이는 경우를 잡는다.
**시트 ③ — 🔴 가장자리(알파) 확대**: 투명 경계 부분을 4배 확대해 3단 비교.
  → **256색 양자화와 손실 WebP가 가장 티 나는 곳이 경계선**이다. 여기가 지저분하면 조각 테두리가 지저분해진다.

시트는 `scratchpad`에 만들고 **저장소에 넣지 않는다.**

### B. 기계 검사 (전수)

투명 픽셀 수 보존 · 긴 변 ≤1200 · 비율 유지(원본 대비 ±0.5% 이내) · 파일 크기 목표 이하 · 디코딩 에러 0

### C. 실제 화면

- 퍼즐 조각이 **정확히 맞물리는지** (마스크는 그림에서 만들어진다 — `_im.onload` → `_bbox`/`_mask`)
- 밑그림(고스트)과 조각이 **어긋나지 않는지**
- 완성 후 확대 연출에서 **테두리가 지저분하지 않은지**

### D. 🔴 실제 폰 (필수)

- **WebP가 실제로 나오는지** (1.7은 "지원한다"까지만 확인한 것)
- 저사양 기기에서 퍼즐 진입이 빨라졌는지 **체감**
- 앱 완전종료 → 재시작 후 확인 (캐시 규칙)

### E. 라이브

curl 200 + 용량 확인 + 전/후 전송량 실측(1.9와 같은 방법)

## 6. ★ 효과 측정 — **`init_timeout`은 이 작업의 지표가 될 수 없다**

> CLAUDE.md 새 규칙: *"효과가 있었는지 무엇으로 아는가를 먼저 정하고 측정 코드를 같이 넣는다."*

### 지적해 주신 `init_timeout`을 확인한 결과

`error-tracker.js:40,227~244`를 읽어보니 `init_timeout`은 **10초 뒤에 `script.js`가 실행을 마쳤고 시작화면(`#ss`)이 있는가**를 본다.

**즉 "첫 화면(시작화면) 로딩"만 감시한다.** 과일 퍼즐은 **시작화면이 이미 떠 있는 뒤에** 들어가는 곳이라, 퍼즐 그림이 아무리 무거워도 `init_timeout`은 **울리지 않는다.**

**1.9의 실측이 이를 뒷받침한다** — 첫 화면 818KB에 과일 그림은 **한 장도 포함되지 않는다.**

→ 🔴 **`init_timeout` 건수는 이 작업 후에도 그대로일 것이다. 이것으로 효과를 판단하면 "효과 없음"으로 잘못 읽는다.**

### 그래서 새로 잰다 — `img_ms`

**퍼즐을 연 순간부터 첫 그림이 화면에 뜰 때까지.** 아이가 빈 화면을 보는 바로 그 시간이다.

| 이벤트 | 파라미터 | 뜻 |
|---|---|---|
| `word_puzzle_open` (기존) | **`img_ms`** (신규) | 퍼즐 열림 → 첫 그림 준비 완료(`_im.onload`) |
| | `category` (기존) | fruit/animal/dino — 이미 보내는 중 |

**측정 코드를 그림보다 먼저 올린다.** 며칠 돌려 **"전" 기준선**을 쌓은 뒤 1단계에 들어간다. C-3 계획서의 `result=off` 기준선과 같은 방식이다.

### 등록할 맞춤 정의 — **1개 추가**

| 종류 | 이름 | 매개변수 | 단위 |
|---|---|---|---|
| **맞춤 측정항목(Metric)** | 그림 대기 시간 | `img_ms` | **밀리초** |

※ `category`는 파닉스 작업 때 이미 등록 목록에 올라가 있다. **추가는 `img_ms` 하나뿐이다.**
⚠️ 숫자이므로 **'측정기준'이 아니라 '측정항목' 탭**이다.

### 무엇을 보고 판단하나

| 보이는 것 | 뜻 |
|---|---|
| `img_ms` 중앙값이 크게 내려감 | ✅ **목적 달성** |
| 안 내려감 | 그림이 아니라 **다른 것이 병목**(개구리 18장 등) — 1.9의 4,474KB 중 그림은 997KB뿐이다 |
| `game_error`(video/script) 증가 | 🔴 WebP를 못 읽는 기기가 있다 → 즉시 되돌림 |
